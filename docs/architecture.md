# Архитектура Backup Pilot

**Статус BP-01, 04.11.2026:** контракты для прототипа BP-04/05/08/12. Реализация
и результаты проверки фиксируются отдельно; согласование Алексеем и Никой ещё требуется.
Ответственный за согласованность: Вадим. Ника проверяет тестируемость, Алексей — совместимость с Astra и упаковкой.

## Пользователь и границы

Пользователь — администратор учебного стенда Astra Linux SE 1.8 x86-64. Он задаёт профиль,
создаёт версионную копию локального каталога, проверяет её и восстанавливает в отдельный каталог.
Работа только с разрешёнными путями. В v1 нет удалённых хранилищ, GUI, инкрементальных копий и шифрования.

Базовый стек: **Python 3.11**, `argparse`, `tomllib`, `pathlib`, `shutil`, `hashlib`, `json`, `unittest`.
Runtime без зависимостей из PyPI; отдельный web-сервис и БД не нужны. Python 3.11.2 доступен в Astra 1.8:
[официальная документация](https://docs.astralinux.ru/latest/start/python/).
Точные версии сборочного окружения и тестового стенда фиксирует Алексей; пользователь запускает `/usr/bin/backup-pilot`.

## Компоненты и контракты

| Компонент (будущий `src/backup_pilot/`) | Вход / результат | Ответственный |
|---|---|---|
| `cli` | Аргументы → вызов сервиса → сообщение и exit code | Вадим |
| `profiles` | TOML → проверенный профиль source/destination/exclude/keep_last/schedule | Вадим |
| `backup` | Профиль → план операций → завершённый snapshot | Вадим |
| `integrity` | Snapshot и manifest → сверка SHA-256 и список нарушений | Ника |
| `retention` | Завершённые snapshot профиля → план удаления старых версий | Вадим |
| `restore` | Проверенный snapshot → отдельный новый каталог | Ника |
| `scheduler` | Профиль и OnCalendar → systemd service/timer и состояние | Алексей |

CLI не реализует копирование напрямую. Модули получают явные пути/настройки и возвращают
структурированный результат либо `BackupPilotError(message, code)`. Внешние команды вызываются
списком аргументов, без `shell=True`.

Контракты прототипа:

- `load_profile(path) -> Profile`, `load_named_profile(directory, name) -> Profile` и
  `list_profiles(directory) -> list[Profile]`. `Profile` хранит name, source/destination
  как Path, exclude как tuple строк, keep_last как int и schedule как str.
- `plan_backup(profile) -> BackupPlan`: только чтение. План содержит проверенный Profile
  и отсортированные относительные пути каталогов и файлов. `execute_backup(plan) -> Path`
  выполняет именно этот план. `list_snapshots(profile) -> list[Path]` возвращает завершённые копии.
- Имя профиля: 1–64 символа ASCII, первая буква/цифра, далее буквы/цифры/`_`/`-`.
  `--profiles-dir` задаёт каталог TOML (по умолчанию `/etc/backup-pilot/profiles.d`).
  Именной запуск читает `<name>.toml`; поле name должно совпадать с именем файла.
  Отдельный `profiles validate --config` принимает произвольное имя TOML-файла.
- Python-модуль запускается с подключённым `src`; исходный запускатель `backup-pilot`
  добавляет его сам. Установку в PATH и `.deb` выполняет BP-17, а не прототип.
- Glob-исключения применяются `fnmatchcase` к относительным POSIX-путям с `/`;
  `*.tmp` совпадает и во вложенных каталогах, `cache/**` исключает содержимое cache.
  Сам cache может остаться пустым. Совпавшие каталоги не обходятся.
- Preview будущих prune/restore/schedule следует тому же контракту: построение плана
  без записи, вывод в stdout, отдельное выполнение после подтверждения. Наличие
  контракта не означает реализацию этих команд.

## Проектный CLI

```text
backup-pilot --help / --version
backup-pilot profiles list
backup-pilot profiles validate --config <profile.toml>
backup-pilot run <profile> [--dry-run]
backup-pilot snapshots <profile>
backup-pilot verify <profile> <snapshot>
backup-pilot prune <profile> --dry-run
backup-pilot prune <profile> --apply
backup-pilot restore <profile> <snapshot> [--to <new-directory>] [--dry-run]
backup-pilot schedule <profile> status|enable|disable [--dry-run]
backup-pilot status
backup-pilot doctor
```

BP-04/05 реализуют help/version, profiles, run и snapshots; BP-08 добавляет `run --dry-run`.
Verify, prune, restore, schedule, status и doctor выше — будущие интерфейсы, не заглушки с кодом успеха.

Контракт exit code: 0 — успех, 2 — неверные аргументы/конфигурация, 3 — отказ доступа,
4 — ошибка ввода-вывода/внешней команды, 5 — нарушение целостности, 6 — профиль занят.
Сообщения содержат причину и действие пользователя, без необработанного traceback и секретов.

## Данные и поток

Профиль TOML: `name`, абсолютные `source` и `destination`, список относительных glob `exclude`,
`keep_last` (целое ≥ 1), `schedule` (systemd OnCalendar). Пример — `examples/profile.toml`.
Именованные профили лежат в отдельных TOML. Все шесть полей обязательны; keep_last
не принимает bool, exclude содержит только непустые относительные glob без `..` и `\\`.
Schedule пока проверяется как непустая строка; синтаксис OnCalendar проверит BP-10.

Вход → валидация → план → preview либо выполнение → метаданные → атомарное завершение → результат.
Snapshot — отдельный каталог `<destination>/<profile>/<UTC-id>/data`.
UTC-id имеет вид `20261104T120000123456Z-<8 hex>`; случайный суффикс исключает коллизии
обычных повторных запусков. Копирование идёт в `.partial-<UTC-id>`; после успешного
копирования записывается `snapshot.json`, затем каталог переименовывается без перезаписи.
При ошибке partial сохраняется для диагностики и не выводится как завершённый snapshot.

`snapshot.json` v1: объект с `schema_version: 1`, `profile`, `snapshot_id`, `completed_at`
(UTC ISO 8601 с timezone). Это свидетельство завершённого копирования, **не проверки целостности**.
Команда snapshots проверяет эти поля, имя каталога и наличие обычного каталога data;
чужие/повреждённые метаданные и partial не считает завершёнными.

Контракт будущего `manifest.json` BP-09: `schema_version: 1`, `profile`, `snapshot_id`,
`files: [{path: "относительный/путь", sha256: "64 hex"}]`. Пути уникальны, относительны,
без `..` и symlink; хеши относятся к байтам скопированных файлов. Ника реализует
создание/валидацию manifest и verify, включая код 5 при повреждении. Until BP-09
прототип не создаёт manifest и не обещает криптографическую проверку.
Блокировка параллельных операций и усиленная защита конкурентных изменений — BP-16.

## Безопасность

- `source` и `destination` не совпадают и не вложены друг в друга после нормализации путей.
  Для учебного v1 symlink и специальные файлы не обходятся; выдаётся понятная диагностика.
- Dry-run не создаёт каталоги, snapshot, manifest, lock-файлы или дисковые журналы и не меняет systemd.
  Вывод плана идёт в stdout. Отсутствие прав не маскируется пустым списком файлов.
- Retention удаляет только завершённые snapshot с распознанным manifest текущего профиля внутри
  разрешённого назначения, сохраняет `keep_last` последних успешных версий; чужие файлы и `.partial-*` не затрагиваются.
  По умолчанию prune показывает план, удаление требует `--apply`. Отдельно проверяется выход через symlink/`..`.
- Restore сначала проверяет manifest и SHA-256. По умолчанию создаётся новый каталог
  `./restored/<profile>-<snapshot>`; существующий каталог или исходный путь не перезаписываются.
  `--to` тоже задаёт новый каталог. Имена из manifest не могут выйти за его пределы.
- Незавершённая копия не считается успешной и не участвует в retention. При ошибке исходные данные
  сохраняются; частичная копия диагностируется. Изменение исходного файла во время чтения — ошибка копирования.
  Прототип сверяет stat до/после копирования; защита от всех гонок подмены путей ещё не реализована.
- Сначала чтение и проверка доступов; административные права только для установки пакета и изменения
  системных unit/timer. Обычные файловые операции выполняются с правами запускающего пользователя.
  Служба использует явно настроенного пользователя с минимальным доступом к профилю.

## Установка и интеграция

Планируемые пути: `/usr/bin/backup-pilot`, `/usr/lib/backup-pilot/`, `/etc/backup-pilot/profiles.d/`,
`/var/lib/backup-pilot/`, systemd-шаблоны `backup-pilot@.service` и `backup-pilot@.timer`
в стандартном каталоге unit-файлов. Расписание включается явно после валидации профиля;
установка пакета не запускает копирование автоматически. Журнал службы — journald.
Изменение расписания сначала проверяется, предыдущая конфигурация сохраняется для отката.
Удаление/обновление пакета не удаляет пользовательские резервные копии. Политику remove/purge
и conffiles проверяет BP-20. Build/package должен давать `backup-pilot_<version>_amd64.deb`.

Полный Linux CLI и упаковка проверяются на реальной Astra-ВМ; контейнер или Ubuntu в CI этого не заменяют.
Готовность и фактические отклонения записываются в `test-plan.md`, архитектура обновляется по реализации.
