# Общие требования ко всем 30 кейсам


## Главный принцип
Это должен быть законченный небольшой продукт, а не набор разрозненных shell-скриптов. После установки пользователь не должен запускать программу из каталога исходников или вручную создавать виртуальное окружение.

## Обязательная структура студенческого репозитория
```text

```

## Инженерные требования
1. CLI/TUI/local web — на выбор команды. GUI не обязателен.
2. Настройки выносятся из исходного кода.
3. Пароли, токены, private keys и реальные секреты в Git запрещены.
4. Root используется только там, где действительно требуется системное изменение.
5. Любое потенциально опасное изменение должно иметь проверку входных данных, preview/dry-run и rollback/backup, если это применимо.
6. Ошибки внешних команд превращаются в понятные сообщения, а не оставляются необработанным traceback.
7. После установки приложение по возможности работает без Интернета; локальный стенд разрешён.
8. Все внешние зависимости фиксируются и документируются.

## Требования к `.deb`
Пакет должен иметь корректные `Package`, `Version`, `Architecture`, `Depends`, `Description`; устанавливать исполняемый файл в системный PATH; конфигурацию — в `/etc/<package>/`, изменяемые служебные данные — в `/var/lib/<package>/`; systemd unit/timer — только если нужен. Он должен устанавливаться, обновляться и удаляться на чистой контрольной ВМ Astra Linux.

Минимальная приёмка:
```bash
sudo apt install ./dist/<package>_<version>_amd64.deb
<package> --help
<package> --version
dpkg -L <package>
sudo apt remove <package>
```

## GitFlic CI
Обязателен `gitflic-ci.yaml` со стадиями как минимум:
```text
lint -> test -> package
```
На `package` должен появляться `.deb` как artifact или файл в `dist/`. Секреты передаются только через CI/CD variables.

## Роли
- Участник 1: application/доменная логика и интерфейс.
- Участник 2: platform/DevOps — Astra Linux, systemd, packaging, CI.
- Участник 3: QA/integration — тесты, стенд, документация, приёмка.
Роли — зоны ответственности, а не запрет работать в других частях. В Git должно быть видно участие всех троих.

## Пошаговый план выполнения проекта

Переходите к следующему этапу только после получения результата предыдущего. План не привязан к неделям или датам занятий.

| Этап | Что сделать | Результат этапа |
|---:|---|---|
| 1 | Прочитать задание целиком и определить пользователя продукта | Команда понимает проблему и итоговый результат; создан GitFlic-репозиторий |
| 2 | Разбить обязательный функционал на небольшие задачи | Созданы issues/backlog с понятными критериями выполнения |
| 3 | Распределить зоны ответственности | Определены ответственные за приложение, Astra/DevOps и QA/интеграцию |
| 4 | Спроектировать минимальную архитектуру | Заполнен `docs/architecture.md`; определены компоненты, данные, права и конфигурация |
| 5 | Сделать минимальный сквозной прототип | Одна главная операция работает от входных данных до результата |
| 6 | Реализовать весь обязательный функционал | Приложение решает основную задачу кейса локально |
| 7 | Добавить валидацию и обработку ошибок | Некорректные данные и типовые сбои дают понятные сообщения |
| 8 | Интегрировать приложение с Astra Linux | Реализована требуемая работа с systemd, сетью, APT, файлами или другими компонентами |
| 9 | Сделать системные операции безопасными | Есть предварительная проверка, `dry-run`, backup/rollback там, где это требуется |
| 10 | Оформить конфигурацию и хранение данных | Настройки вынесены из кода, форматы и пути описаны |
| 11 | Написать автоматические тесты | Unit-тесты, validation tests, минимум один integration/smoke test и отказной сценарий |
| 12 | Собрать первый `.deb` | Пакет устанавливается на Astra Linux и приложение запускается из системного PATH |
| 13 | Настроить GitFlic CI | Pipeline автоматически выполняет `lint → test → package` |
| 14 | Проверить проект на чистой Astra Linux | Новый пользователь может установить `.deb` и выполнить основной сценарий только по README |
| 15 | Выполнить все приёмочные сценарии | `docs/test-plan.md` содержит фактические PASS/FAIL |
| 16 | Завершить документацию | Готовы README, architecture, user guide, admin guide, test plan и demo |
| 17 | Подготовить финальный релиз | Версия согласована, создан tag/release, сохранён финальный `.deb` |
| 18 | Подготовить защиту | Команда может за 7–10 минут показать установку, работу, отказной сценарий, CI и вклад участников |

### Как понять, что можно идти дальше

Следующий этап начинается не по календарю, а после выполнения результата предыдущего.

- Не переходите к упаковке в `.deb`, пока основная функция приложения не работает.
- Не настраивайте CI, пока команды тестирования и сборки не работают локально.
- Не добавляйте необязательные функции, пока не закрыт обязательный функционал.
- Не считайте проект готовым, пока `.deb` не проверен на чистой Astra Linux.
- Если обнаружен дефект предыдущего этапа, вернитесь и исправьте его.

## Definition of Done
Все обязательные функции реализованы; acceptance пройден; CI зелёный; `.deb` устанавливается на чистую Astra Linux; README позволяет установить и использовать продукт без преподавателя; есть архитектура, user/admin guide, test plan, demo script; создан финальный tag/release.

## Методика последовательного выполнения проекта

Работа по каждому кейсу организуется по принципу достижения проверяемых инженерных результатов, а не по календарному графику. Индивидуальный маршрут приведён непосредственно в `README.md` соответствующего кейса.

Общая логика жизненного цикла включает: формализацию требований; архитектурное проектирование; минимальный сквозной прототип; последовательную реализацию предметных подсистем; интеграцию с Astra Linux; обработку отказов; автоматизированные испытания; Debian-пакетирование; GitFlic CI; испытания на чистой операционной системе; приёмку и выпуск релиза.

**Критерий перехода между этапами:** результат текущего этапа должен быть воспроизводим другим участником команды по документации и содержимому репозитория.
