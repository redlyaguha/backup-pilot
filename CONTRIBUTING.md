# Совместная разработка

## Ветки и pull request

- Основная ветка: `prod`. Интеграционная ветка: `dev`.
- От `dev` создавать `feature/BP-04-cli`, `fix/BP-12-permissions`, `test/BP-11-dry-run`,
  `docs/BP-19-user-guide` либо `ci/BP-22-actions`. Префикс `chore/` тоже разрешён.
- Одна задача — один небольшой PR в `dev`. В описании указать `Closes #<номер>`,
  выполненные критерии приёмки, проверку и известные ограничения.
- Автор не одобряет свой PR. Нужно минимум **одно одобрение другого участника с Write**,
  успешные `repository-structure` и `branch-policy`, устранённые замечания.
  Продуктовые проверки добавляются в обязательные по BP-22.
- Новые коммиты сбрасывают старое одобрение. Feature-ветка должна учитывать актуальную `dev`.
  Прямые push, force-push и удаление `dev`/`prod` запрещены, в том числе администратору.
- Функциональные PR в `dev` объединять через **Create a merge commit**, сохраняя коммиты участников.
- Релизный PR открывать строго **`dev` → `prod`**. Провести повторное ревью и повторные проверки.
  Сливать через **Create a merge commit**, чтобы сохранять общую историю долгоживущих веток.
  Обратное слияние `prod` в `dev` не требуется: изменения в `prod` появляются только из `dev`.
  Для релизного PR проверяется результат слияния; требование включить предыдущий merge commit
  `prod` в историю `dev` отключено, чтобы не создавать цикл веток.
- После слияния удалять только свою короткую ветку. `dev` не удалять после релизного PR.
- Форки не используются для рабочего процесса команды; проверка направления требует ветки этого репозитория.

## Очередь ревью

| Автор PR | Основной рецензент | Запасной |
|---|---|---|
| Вадим | Алексей | Ника |
| Алексей | Ника | Вадим |
| Ника | Вадим | Алексей |

Для релизного PR действует то же правило: автор получает одобрение другого участника.
Рецензент проверяет требования issue, изменения файлов, ошибки и безопасность, запускает относящиеся
к задаче проверки. Крупные изменения восстановления или удаления дополнительно просматривает третий участник.
Перед контрольной точкой оставлять один день на ревью; сообщать о блокировке в issue.

## Коммиты и честная отчётность

Использовать собственный Git-аккаунт и содержательные коммиты: `feat:`, `fix:`, `test:`, `docs:`, `ci:`.
Начальная организационная заготовка подготовлена Codex через аккаунт Вадима;
она не заменяет индивидуальные коммиты и ревью студентов. Не создавать коммиты от чужого имени
и не отмечать непроверенные сценарии PASS.

## Готовность задачи

Критерии из issue выполнены; код и документация согласованы; добавлены относящиеся к изменению
тесты; проверки воспроизводимы; секретов нет; получено ревью. Для системных задач приложить
версию Astra, команды, ожидаемый и фактический результат. Приёмка продукта — только на чистой Astra SE 1.8.

В Git не добавлять пароли, ключи, токены, `.env`, venv, реальные резервные копии, персональные данные,
образы ВМ и журналы с содержимым пользовательских файлов. Примеры используют только учебные пути.
